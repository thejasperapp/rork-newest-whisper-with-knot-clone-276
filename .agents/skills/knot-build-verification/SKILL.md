# Build Verification

A successful build command proves execution, not that its output exists or works. Keep build/static validation separate from runtime evidence.

## Four checks

1. Exists: independently inspect the actual new artifact at the measured path and nonempty expected size after writing. A filename printed by the generator is not existence evidence. Keep exact task ownership and measured final identity.
2. Loads: for a runnable page or game, open the same final build through a genuinely available authorized browser/headless surface at 390 by 844 and 1280 by 800. Capture actual runtime/console errors. A syntax pass, mocked DOM or another build's screenshot is not loading evidence.
3. Responds: drive the primary user journey with real input and real wall-clock time. For a game, exercise the first minute when the available owned deadline permits: start, movement, primary action and a reachable failure state. Frozen or synthetic clocks can support unit tests but are not a real gameplay/playtest receipt.
4. Looks: inspect screenshots from that driven session at both viewports. Blank canvases, overlap, missing styles and unreadable layouts are failures, regardless of exit status.

## Repair and report

Fix a confirmed failure with a genuinely new owned correction and reverify the changed artifact; preserve prior/rejected files and the no-replay latch. Never rerun an uncertain dispatched command or expand execution time or browser authority to satisfy this guide. Ordinary command and skill caps do not apply: work uses the shared runaway ceiling, plumbing is unmetered, and complete installed guides are reused only from the same actual owned session with original provenance.

Describe only observed results: which build, viewports and actions actually ran, what succeeded and any missing check. Do not claim 'played the first level' if only the title screen appeared. Reading source is not testing; a screenshot alone verifies no interaction.

If the runtime surface is absent or the deadline cannot support a real first minute, record exactly what remains unverified in Events. Chat presents only the actually delivered artifact, without shortfall or promise narration. An actual captured artifact can be delivered with recorded shortfalls only where the existing delivery policy permits it. Never turn missing mandatory proof/capture into an unverified-success bypass or fabricate a delivered artifact.

## Capability boundaries

Do not open private/authenticated sites, submit forms, install tools, mutate browser profiles or fabricate runtime receipts to obtain proof. Local artifact/headless work requires its actual advertised owned execution surface; the public-page browser cannot be repurposed into private workspace access. This craft guidance grants no extra tools and does not replace required live guide reads, independent document proof/content review or immutable capture.
